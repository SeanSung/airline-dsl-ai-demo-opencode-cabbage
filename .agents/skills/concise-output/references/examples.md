# 简洁输出参考

## 禁用短语

| 禁用 | 原因 |
|--------|-----|
| “我来帮你处理” | 直接帮即可 |
| “让我解释一下……” | 直接解释 |
| “值得注意的是” | 删除 |
| “正如我们之前讨论的” | 不必要 |
| “为了……”（in order to） | 用“to” |
| “此外”/“另外” | 通常可删 |
| “基本上”/“本质上” | 直接说 |
| “我认为”/“我相信” | 直接陈述 |
| “正如你所见” | 对方能看见 |

## 错误 vs 正确

冗长：

```
值得注意的是，在我们开始之前……让我解释一下……
```

简洁：

```
架构问题：[问题]。建议[方案]。
```

元评论 → 直接的编号要点。
冗长的 README 欢迎语 → 给出 Node 18+、安装/测试/启动的快速上手。
冗长的提交散文 → 主题 + 一行原因。
冗长的计划铺垫 → 带文件路径的编号计划。

## 密度技巧

| 技巧 | 示例 |
|-----------|---------|
| 删掉引子 | 跳过“以下是修复：”——直接展示修复 |
| 使用表格 | 散文 → 结构化对比 |
| 行内化上下文 | “`npm test` 验证” |
| 删掉赞美 | 跳过“好问题！” |
| 跳过显而易见 | 别复述清晰代码 |

## 自我合理化借口

| 借口 | 现实 |
|---|---|
| 友好的开场白有帮助 | 延迟价值交付 |
| 先解释推理 | 先给结果；非显而易见处再论证 |
| 更多细节更安全 | 稀释关键事实 |
| 列表显得生硬 | 列表便于扫读；散文掩盖结构 |
| 复述问题以确认 | 直接回答；答错会更快暴露误读 |
