# 项目上下文文档

当头脑风暴绑定到一个本地项目，并可能沉淀出持久术语、边界、关系或难以逆转的决策时阅读本文。

## 目录

- 持久化边界
- 查找上下文文档
- 惰性文件创建
- 会话期间
- `CONTEXT.md` 格式
- ADR 规则与格式

## 持久化边界

持久知识只通过项目自有的上下文文档留存：

- `CONTEXT.md`：术语表条目、领域边界和关系。
- 已有的 `CONTEXT-MAP.md`：对于已存在多个 context 的仓库。
- `docs/adr/*.md`：稀疏的架构决策记录。

不要创建单独的会话日志、隐藏的本地持久化目录、检查点文件、恢复缓存、引文日志或任何技能私有数据目录。

## 查找上下文文档

在首次实质性回答前，只查阅与主题相关的窄范围文件：

- 如果项目根存在 `CONTEXT-MAP.md`，先读它。然后只读相关 context 的 `CONTEXT.md` 文件和适用的 `docs/adr/*.md`。
- 如果不存在 `CONTEXT-MAP.md` 但根目录有 `CONTEXT.md`，把项目视为单一 context，读该文件及适用的 `docs/adr/*.md`。
- 如果两者都不存在，正常继续。不要提 `CONTEXT-MAP.md`，也不要建议创建它。

## 惰性文件创建

只有在有持久内容要写时才创建文件：

- 如果不存在 `CONTEXT.md`，在首个领域术语、边界或关系被确定时创建。
- 如果不存在 `docs/adr/`，只在达成首个值得记 ADR 的决策时创建。
- 当项目尚未有 `CONTEXT-MAP.md` 时，不要创建或建议创建它。如果它已存在，只在新 context 或关系被明确确认时更新。

## 会话期间

- 用现有 `CONTEXT.md` 术语挑战用户语言。如果术语表以一种方式定义了某术语，而用户似乎意指另一种，立即指出冲突并问应以哪个含义为准。
- 在继续前提出一个精确的规范术语，以磨砺模糊语言。
- 当领域关系模糊时，使用具体场景和边界情况。
- 当用户陈述某物如何工作时，与代码交叉核对。如果代码与对话相互矛盾，亮出矛盾并问哪个来源是权威。
- 当一个术语被确定，就地更新相应的 `CONTEXT.md`，而不是把更新攒到会话末尾。

## `CONTEXT.md` 格式

`CONTEXT.md` 只是术语表。它不得包含实现细节、草稿笔记、任务叙述、specs、计划或内存转储。

优先使用现有本地格式。若新建文件，使用：

```markdown
# Context

## Glossary

- **Term**：用业务/领域语言给出的定义。当它能防止与邻近术语混淆时，包含边界。
```

好条目：

```markdown
- **Sponsor（赞助人）**：能为内部项目出资、配人或在政治上捍卫它的人。赞助人不一定是日常用户。
```

坏条目：

```markdown
- **Sponsor（赞助人）**：存储在 `users.sponsor_id` 列，由 `SponsorService` 处理。
```

## ADR 规则与格式

仅当以下三条全部成立时才提议 ADR：

1. **难以逆转**——以后改变该决策有显著成本。
2. **没有上下文会令人惊讶**——未来读者会奇怪为什么选了这条路。
3. **真实权衡**——曾存在真正的备选，因具体理由选了其中一个。

任一条件不满足，跳过 ADR。

在 `docs/adr/` 下按顺序编号。优先使用现有本地格式。若创建首个 ADR，使用：

```markdown
# 0001-short-title

## Status

Accepted

## Context

是什么压力或约束迫使做出这个决策？

## Decision

我们选择了什么？

## Consequences

什么变得更容易、更困难，或被有意置于范围之外？
```
