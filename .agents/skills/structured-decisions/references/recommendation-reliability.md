# 推荐可靠性

在头脑风暴会话中做出非平凡推荐前使用本参考。目标是降低决策噪声，同时不暴露原始思维链或把回答变成会议纪要。

## 触发条件

当一个错误答案会实质影响以下方面时，该推荐即是非平凡的：

- 架构边界、API 契约、数据模型或长期维护；
- 产品方向、定位、定价、采用或用户工作流；
- 团队流程、项目治理、迁移成本或难以逆转的选择；
- 证据薄弱但下游后果显著的决策。

对命名打磨、轻量构思、低风险偏好，或二次检查不会改变结果的显而易见的本地选择，跳过本检查。

## 二次采样通过

在收敛于一个非平凡推荐之前，内部跑一次 `二次采样通过`（second-sample pass）：

1. 在内部陈述第一个推荐。
2. 从另一个具名视角重新评估决策，例如怀疑的买家、目标用户、未来维护者、调用方、运维、竞争者、评审者或预算所有者。
3. 将第二个结果与第一个推荐比较。
4. 决定是保留推荐、改变它、降低置信度，还是问一个阻塞问题。

不要暴露原始思维链。只有当它改变了用户需要知道的内容时，才披露一段决策轨迹摘要。

## 输出规则

如果二次采样通过是稳定的，隐藏检查，只输出带简洁理由的最终推荐。

如果二次采样通过不稳定，包含一段简短的 `二次采样检查`：

```text
二次采样检查：
- 首个推荐：<A/B/C>
- 二次采样结果：<改变了的推荐或更低的置信度>
- 分歧来源：<假设、约束、证据缺口或风险>
- 最终动作：<改变推荐、保留但降低置信度，或问一个阻塞问题>
```

对高影响决策，当用户需要置信度来源时也展示该检查，但只围绕决策节点，而非隐藏推理。

## 决策圆桌

对高复杂度的非平凡推荐，把二次采样通过升级为 `决策圆桌`（Decision Roundtable）。这是一个升级机制，不是第四种头脑风暴姿态。

当至少出现两个复杂度信号，或用户明确要求圆桌、subAgent、多专家或独立视角分析时升级：

- 对架构、产品方向、用户工作流或治理的高影响；
- 采纳后难以逆转；
- 调用方、维护者、用户、运维、安全、性能、业务或迁移需求之间视角冲突；
- 证据薄弱但下游后果高；
- 外部现实或生态最佳实践可能实质改变推荐。

默认使用 3 个独立视角，至多 5 个。为具体问题挑选视角，而不是使用固定专家列表。对架构问题，有用的默认是：

- 调用方/用户契约：调用方体验、接口边界、误用风险；
- 未来维护者：复杂度、可读性、迁移和测试面；
- 可靠性/运维：性能、失败模式、可观测性、恢复。

每个视角必须独立产出一个推荐，而不仅是评论。主助手充当裁判：比较假设、风险、证据质量、可逆性和本地约束。不要靠投票决策；当少数视角识别出严重的不可逆风险时，它可以推翻多数。

## 圆桌输出

如果圆桌稳定，隐藏圆桌，只输出带简洁理由的最终推荐。

如果分歧影响最终推荐，包含一段压缩的 `圆桌检查`：

```text
圆桌检查：
- 一致：<哪些视角对齐>
- 分歧：<哪个视角反对以及为什么>
- 最终动作：<改变推荐、保留但降低置信度，或问一个阻塞问题>
```

只有当用户明确要求查看圆桌时，才把每个视角展开为 3-5 条要点。

## 外部校准席位

外部校准是一个可选的圆桌席位，不是默认席位。

仅当外部现实能实质影响决策，或用户明确要求外部指引时使用。实时搜索前，使用 `SKILL.md` 中的外部校准隐私闸门：展示概括性搜索词，请用户确认、修改或跳过。不要搜索项目名、公司名、专有概念、客户名或敏感细节。

外部席位不投票。它回答：

- 常见做法：成熟用户或生态通常怎么做；
- 当前警示：哪些近期或真实世界失败模式重要；
- 影响：这对当前推荐意味着什么。

如果外部建议与本地证据或用户的一手经验冲突，点名冲突，并在收敛前问应以哪个真相来源为准。
