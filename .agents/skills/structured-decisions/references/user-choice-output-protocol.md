# 用户选择输出协议

当头脑风暴会话到达一个面向用户的选项集时使用本参考。阻塞式停顿优先使用宿主原生选择 UI，而非散文。文本块仅作回退。

用于姿态选择、前提批准、方案选择、范围权衡、终局收敛，以及任何必须在头脑风暴会话继续之前解决的选择。不要对每个轻量澄清都用它。

## 目录

- 决策简报
- 推荐可靠性检查

## 决策简报

在选择宿主输出格式前准备这份简报：

- `D<N>` 编号和短标题。
- 一句话问题。
- 通俗语言的利害：依选择不同，什么会变得更好或更糟。
- 推荐及理由。
- 2-3 个互斥选项。
- 每个选项：标签、收益、代价/风险，以及何时适合。
- 当选项因覆盖范围不同时加完备性说明，或当覆盖范围不可比时写"选项属不同性质"。
- 对非平凡推荐的可靠性说明：稳定的 `二次采样通过`、披露的 `二次采样检查`，或 `决策圆桌`。
- 净影响：所选选项会改变下游什么。

## 推荐可靠性检查

在呈现非平凡推荐前，遵循 `recommendation-reliability.md`。稳定的可靠性检查保持隐藏，选项集只展示最终推荐。不稳定的检查必须在选项集前披露一段简短的 `二次采样检查`。高复杂度决策可使用 `决策圆桌`；若分歧影响最终推荐，披露一段压缩的 `圆桌检查`。

绝不暴露原始思维链。可见输出是一段决策轨迹摘要：推荐、分歧来源、置信度变化和最终动作。

## 阻塞式选择与终局选项

结构化选择是一次阻塞式停顿，不是展示选项的唯一方式。仅当会话需要用户选 A/B/C 之后下一步推理才成立时使用它。

当助手能推荐一个方向且不再有阻塞选择时，用终局 A/B/C 选项作为默认收敛形态。同样的可见选项格式出现在阻塞和终局两种情形；只有最终指令不同。

在使用原生选择工具、MCP 征询、gstack `AskUserQuestion` 或回退 A/B/C 文本做阻塞停顿后，立即停止并等待。不要在同一回合追加决策总结或推荐回顾。

## 严格自检

在调用结构化选择工具或为阻塞停顿发出回退文本前，核实：

- `D<N>` 标题存在，并从上一个决策递增。
- 问题只问一个决策，而非多个隐藏决策。
- 选项互斥并覆盖现实路径。
- 推荐项在 Codex 中排第一，在所有其他宿主中标注 `(Recommended)` 或 `(recommended)`。
- 推荐有具体理由，而非"最佳平衡"却不说在平衡什么。
- 非平凡推荐已通过稳定的 `二次采样通过`，或披露了改变推荐/置信度的 `二次采样检查`/`圆桌检查`。
- 利害明确：若用户选错，什么会变糟。
- 完备性仅在覆盖范围不同时打分；否则用性质说明。
- 优/劣满足下方质量门槛。
- 提问后回应停止，等待用户回答。

任一项不通过，先重写问题再问。

## 优/劣质量门槛

每个真实选项必须包含：

- 至少一条与用户结果挂钩的具体收益。
- 至少一个诚实的代价、风险或丧失的备选。
- 除非宿主格式太短，否则有"何时适合"条件。
- 来自当前主题的具体名词。避免空词如"简单"、"灵活"、"健壮"或"更好"，除非后面接明什么变得更简单、灵活或更好。

对 gstack AskUserQuestion 这类富宿主，非平凡决策每选项至少用两条优和一条劣。对紧凑的 Codex `request_user_input`，把最强的收益和代价/风险压缩进选项描述。

坏例子：

```text
A) 快
   好：快
   代价/风险：较不完整
```

好例子：

```text
A) 最小协议修复（推荐）
   好：修复了虚假的 Claude Code AskUserQuestion 契约，且不扩张运行时依赖。
   代价/风险：把更宽的办公时间诊断留到单独迭代。
   何时适合：目标是以最小持久编辑纠正宿主兼容性时。
```

## Codex 宿主格式

Codex 原生选择 UI 是 `request_user_input` 工具。当它在当前回合的可用工具中列出时使用。Codex Default 模式在 `DefaultModeRequestUserInput` 特性启用时暴露它。

Codex 用户可在 `~/.codex/config.toml` 中启用 Default 模式原生选择：

```toml
[features]
default_mode_request_user_input = true
```

若当前宿主是 Codex 但未列出 `request_user_input`，发出回退 A/B/C 决策块并停止。不要要求用户更改协作模式。回退是纯 Markdown，因此不得调用或暗示它是 Codex 原生选项 UI。

工具可用时，每个停顿点只问一个决策问题。

使用此形态：

```json
{
  "questions": [
    {
      "header": "<最多 12 字符>",
      "id": "<stable_snake_case_id>",
      "question": "<一句话问题>",
      "options": [
        {
          "label": "<短标签> (Recommended)",
          "description": "<一句话影响或权衡>"
        },
        {
          "label": "<短标签>",
          "description": "<一句话影响或权衡>"
        }
      ]
    }
  ]
}
```

规则：

1. 问一个决策问题，然后停止并等待。
2. 提供 2-3 个互斥选项。
3. 把推荐项放第一，其标签后缀 `(Recommended)`。
4. `header` 不超过 12 字符。
5. 使用稳定的 snake_case `id`。
6. 标签保持短，把权衡放进 descriptions。
7. 不要加"Other"选项。Codex 客户端可能自动添加自由形式 Other。

字段映射：

- `header`：最短的有用标题，而非完整 `D<N>` 行。
- `id`：snake_case 的决策标题，跨重试稳定。
- `question`：一句话，自然时可包含推荐。
- `options[].label`：1-5 个词，只有首项带 `(Recommended)`。
- `options[].description`：一句话，含收益和代价/风险。仅在完备性改变决策时才包含。

## Claude Code MCP 征询

当宿主是 Claude Code 时，使用 MCP 征询作为必需的结构化输入路径，除非官方 Claude Code / MCP 协议改变。不要仅仅因为其他宿主使用不同选择机制，就把 Claude Code 降级为散文或通用结构化输入。

最小形态：

- 单选字段，枚举值为 `A`、`B`，以及可选的 `C`。
- 字段 prompt 包含一句话问题和利害。
- 选项标签包含短标签和推荐标记。
- 字段或选项描述包含推荐、收益和代价/风险。

如果 Claude Code 运行时声称支持 skills 但未向当前 agent 暴露 MCP 征询，在使用回退文本块前明确说明缺失的宿主能力。不要用 Markdown、XML、注释或假工具调用模拟 MCP 征询。

## gstack AskUserQuestion 格式

当 gstack 风格宿主暴露真实的 `AskUserQuestion` 工具时，把决策简报作为工具调用发送，而非散文。不要用写 Markdown 来模拟。

在工具内使用此内容形态：

```text
D<N> - <一句话问题标题>
Project/branch/task: <一句简短扎根句，或 "头脑风暴会话：<主题>">
ELI10: <用通俗语言解释选择和利害，2-4 句短句>
选错的利害：<什么会坏、用户失去什么，或什么讨论路径变得浪费>
推荐：<选项>，因为<一行理由>
完备性：A=X/10, B=Y/10
  或：注意：选项属不同性质，非覆盖范围差异——不打完备性分。
优/劣：
A) <选项标签> (recommended)
  好：<具体收益，针对当前主题>
  好：<非平凡决策的第二条具体收益>
  代价/风险：<诚实的坏处或丧失的备选>
  何时适合：<此选项正确的条件>
B) <选项标签>
  好：<具体收益，针对当前主题>
  好：<非平凡决策的第二条具体收益>
  代价/风险：<诚实的坏处或丧失的备选>
  何时适合：<此选项正确的条件>
C) <选项标签，可选>
  好：<具体收益，针对当前主题>
  好：<非平凡决策的第二条具体收益>
  代价/风险：<诚实的坏处或丧失的备选>
  何时适合：<此选项正确的条件>
净：<权衡的一行综合>
```

规则：

1. skill 调用中的第一个决策是 `D1`；之后每个决策递增。
2. `ELI10` 始终存在且通俗。
3. 推荐始终存在，包括中立的品味判断。
4. 恰好在一个选项上标注 `(recommended)`。
5. 仅当选项覆盖范围不同时用完备性评分；否则用性质说明。
6. 保持选项互斥。
7. 非平凡决策每选项至少两条优和一条劣；单向硬停止确认可声明不存在真实备选。
8. 工具调用后停止并等待。

## 回退文本

如果没有结构化选择工具可用于阻塞停顿，发出以下固定文本块并停止：

```text
D<N> - <决策标题>
问题：<一句话问题>
利害：<依选择不同什么会变得更好或更糟>
推荐：<A/B/C>，因为<理由>
完备性：<覆盖范围评分或 "选项属不同性质">
选项：
A) <标签> (recommended)
   好：<收益>
   代价/风险：<代价或风险>
B) <标签>
   好：<收益>
   代价/风险：<代价或风险>
C) <标签，可选>
   好：<收益>
   代价/风险：<代价或风险>
影响：<下游改变什么>
回复 A、B 或 C。
STOP：在继续前等待用户回答。
```

回退规则：

1. 不要把回退块称为原生选择器。
2. 提问后不要在同一回合继续。
3. 不要发明 XML 标签、注释或隐藏协议标记。
4. 在 Codex 中，当 `request_user_input` 不可用时，把此回退用于真实决策停顿，并等待用户回复 A、B 或 C。

## 终局选项

终局收敛时，即使选项有用但非阻塞，也保持同样的 A/B/C 选项形态。使用此形态：

```text
- 推荐：<A/B/C>，因为<为什么此方向胜出>
- 已定决策：<已经确定的内容>
选项：
A) <推荐方向> (Recommended)
   好：<收益>
   代价/风险：<代价或风险>
B) <备选>
   好：<收益>
   代价/风险：<代价或风险>
C) <备选，可选>
   好：<收益>
   代价/风险：<代价或风险>
- 开放问题：<仍重要的未知项>
```

规则：

1. 当存在用户日后仍可能选择、拒绝或组合的有意义路径时，使用终局选项。
2. 把推荐项放第一并标注 `(Recommended)`。
3. 终局选项不要说"回复 A、B 或 C"；该措辞保留给阻塞停顿。
4. 选项前始终包含 `推荐：<A/B/C>，因为<理由>`。
5. 选项保持足够短，使推荐仍易于扫读。
