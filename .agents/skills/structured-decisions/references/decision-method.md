# 结构化决策方法

当对话需要超出轻量回答的深度时阅读本文：产品诊断、技术方向、外部校准、非平凡选项比较，或终局收敛。

## 对抗性澄清

不做廉价表扬。帮用户思考；不要让一个薄弱的想法看起来已经完成。在推荐、收敛或强化一个重要方向之前，先跑一轮冷水检验。根据利害程度调节强度。

冷水检验应回答：

- 这最可能在哪里崩掉？
- 哪些隐藏假设承担了最多分量？
- 哪些证据缺失、薄弱，或仅建立在信心之上？
- 一个怀疑的买家、竞争者、维护者、投资人、评审者，或未来后悔的自己会怎么说？
- 如果这个想法在挑战后幸存，它为什么能幸存？

有用的压力测试：

- 在把一个方向当作持久方向之前，问"什么会让它崩掉？"。
- 在生成选项前，点名最强的隐藏假设。
- 对重要的产品、工作流或架构选择，跑一个简短的事前验尸（pre-mortem）。
- 对技术方向，跑一次不友好的设计评审：过度工程、契约不清、不安全的默认值、隐藏耦合、缺失测试面。
- 对产品或定价想法，从怀疑的买家、有偏见的投资人或竞争者的视角论证。
- 如果一个选项听起来不错只是因为某个难点没被点名，直接点名那个难点。

## 详细工作流

1. **框定主题**
   - 用一两句话复述用户目标。
   - 直接点出模糊之处。
   - 若本地上下文重要，只查阅最少量的必要证据。
   - 若用户从一个细节出发，先拉远：参与者、接触面、约束、现有替代方案，以及真正的决策。

2. **选择姿态**
   - 产品诊断：客户、收入、采用、赞助人、创业、内部产品，或"值不值得做？"类问题。
   - Builder 模式：副业、黑客松、开源、学习、调研、demo、玩具、创意工具。
   - 通用决策：战略、命名、技术方向、工作流、API、架构、设计方向，或模糊的早期思考。
   - 若姿态选择会改变对话走向且并不显而易见，问一个结构化选择问题。

3. **有针对性地提问**
   - 当答案会改变方向时，一次只问一个问题。
   - 先解决上游选择，再处理下游细节。
   - 对每个非平凡问题，附上你推荐的答案和理由。
   - 已被 prompt 或本地证据回答的问题，智能跳过。
   - 若用户不耐烦，至多再问两个关键问题，然后进入前提挑战和选项，除非明显需要外部校准。

4. **挑战前提**
   - 问这是否是正确的问题，或是否存在更简单的框定。
   - 问如果什么都不变会怎样。
   - 把期望的解决方案与底层的 job、痛点或决策分开。
   - 对产品想法，把兴趣与需求分开，把具名用户与宽泛类别分开。
   - 对 builder 想法，把有趣的核心与打磨、基础设施和过早优化分开。
   - 对技术想法，把调用方可见的契约与内部机制分开。

5. **生成选项**
   - 提供 2-3 个不同的方案、概念或方向。
   - 让选项有实质差异，而非表面变体。
   - 对非平凡推荐，在选定胜出者前阅读 `recommendation-reliability.md`。
   - 证据足够强时，把推荐项放在最前。
   - 每个选项集必须恰好包含一个推荐项和一条具体理由。
   - 对非平凡的产品或技术选择，在这种切分合适时，包含一个最小可行选项、一个理想长期选项和一个创意/侧向选项。

6. **对选项做压力测试**
   - 检查假设、失败模式、隐藏复杂度、受众契合度和约束。
   - 用具体场景和边界情况暴露模糊或冲突的想法。
   - 点名被重载的术语，在继续前提出一个精确含义。
   - 若本地证据与用户的模型矛盾，亮出矛盾并问应以哪个来源为准。
   - 移除不服务于用户所述目标的想法。

7. **收敛**
   - 不要直接从用户偏好的答案收敛。
   - 先陈述冷水检验结果，再修正、问一个阻塞问题，或解释为什么该方向能幸存。
   - 对非平凡推荐，只有在稳定的二次采样通过或披露了二次采样检查后才收敛。
   - 把已定决策与开放问题分开记录。

## 外部校准

仅在用户目标、判断标准和关键约束已足够清晰，外部信息能够挑战一个真实前提时才运行。

仅当外部现实能实质改变讨论时触发：产品、市场、采用、设计或技术生态、当前最佳实践、竞争者、替代品、在位工作流、对趋势敏感的推荐、用户要求外部声音，或对话明显依赖过时假设的风险。

实时搜索前，暂停做隐私闸门。展示概括性的搜索词，请用户确认、修改或跳过。不要搜索项目名、公司名、专有概念、客户名或敏感细节。

保持轻量：读 2-3 个高信号来源，优先一手或信誉来源，使用实时来源时保留链接。综合：常识、当前讨论，以及对我们前提的影响。外部校准只喂给前提挑战；它不是最终裁判。

## 核心决策动作

- **拉远地图（Zoom-out map）：** 在请求选择前，给出周边系统、受众、工作流、概念或权衡的简短地图。
- **决策树追问（Decision-tree grilling）：** 一次问一个消解分支的问题。
- **推荐答案（Recommended answer）：** 提供一个默认答案，用户可以快速接受、拒绝或纠正。
- **语言磨砺（Language sharpening）：** 用精确术语替换模糊或被重载的词。
- **场景探针（Scenario probe）：** 用一个具体例子、边界情况或失败案例检验想法。
- **激进选项拆分（Radical option split）：** 迫使选项在战略、约束、用户、架构或风险轮廓上有所不同。
- **单问题原型框定（One-question prototype framing）：** 若用户想尝试某样东西，确定原型要回答的那一个问题，但不要去构建它。
- **证据优先于盘问（Evidence over interrogation）：** 查阅廉价的本地证据，而不是向用户索要仓库能回答的事实。

## 模式路由

| 信号 | 模式 | 首个压力 |
| --- | --- | --- |
| 客户、收入、采用、赞助人、市场、创业、值不值得做 | 产品诊断 | 存在需求，还是仅存在兴趣？ |
| 副业、黑客松、开源、学习、调研、demo、好玩 | Builder 模式 | 最酷的可分享版本是什么？ |
| 战略、命名、技术方向、工作流、API、架构、不清楚的想法 | 通用决策 | 在细节上游的决策是什么？ |

产品诊断阶段路由：

- **产品前：** 优先需求现实、现状和具体的人。
- **已有用户：** 优先现状、最窄楔子和观察。
- **已有付费客户或承诺赞助人：** 优先最窄楔子、观察和未来适配。
- **纯工作流或工程工具：** 优先现状和最窄楔子。
- **内部项目：** 把"为它付费"翻译为赞助、采用、配人或在政治上捍卫它。

Builder 模式路由：

- 若用户想要惊喜，从最酷版本和他们会展示给谁开始。
- 若用户想快速发布，从最快可用或可分享路径开始。
- 若用户想要差异化，从最接近的现有东西以及它如何不同开始。
- 若中途出现商业利害，切换到产品诊断并说明原因。

## 技术决策视角

对技术方向、API、模块、工作流或架构选择，停留在设计层，评估：

- 谁使用它：调用方、用户、维护者、运维、测试或外部系统。
- 它必须做什么：关键操作、不变量、顺序、错误和兼容性约束。
- 它隐藏什么：应藏在接口背后的复杂度。
- 正确使用的容易度：常用路径是否显而易见，危险路径是否难以意外触发。
- 深度：一个小表面是否给出有用的杠杆。
- 删除测试：如果删除该单元会让复杂度消失，它可能不必要；如果复杂度扩散到许多调用方，它大概在挣自己的位置。
- 过度泛化风险：灵活性是否解决了真实的近期需求。

## 产品诊断姿态

操作规则：

- 像"开发者"、"中小企业"或"团队"这样的宽泛类别是不够的。
- 把行为、金钱、重复使用、坏掉时的愤怒和工作流依赖视为需求。
- 把赞美和等待名单视为弱证据。
- 当前的 workaround 才是真正的竞争者。
- 不要从弱需求证据生成强推荐。

问题库，一次问一个并智能跳过：

1. 除了兴趣或注册，有人真正想要它的最强证据是什么？
2. 他们今天如何解决它（哪怕很糟），代价是什么？
3. 谁最需要它，他们的角色是什么，他们在避免什么后果？
4. 很快有人会为之付费或在政治上赞助的最小版本是什么？
5. 你是否看过某人在没有你帮助的情况下尝试它，什么让你惊讶？
6. 如果世界在三年后改变，这会变得更必要还是更不必要？

## Builder 模式姿态

操作规则：

- 惊喜很重要。找到会让某人说"哇"的东西。
- 可发布很重要。优先用户真正能用或展示的版本。
- 若用户为自己构建，把这当作有用证据信任。
- 在把奇怪的想法优化掉之前先探索它。

问题库，一次问一个并智能跳过：

1. 这东西最酷的版本是什么？
2. 你会展示给谁，什么会让他们在意？
3. 到可用或可分享之物的最快路径是什么？
4. 最接近的现有东西是什么，这有什么不同？
5. 如果时间无限，10 倍版本是什么？

## 输出形态

根据用户需要缩放回答。轻量构思可以是一份带推荐的短列表。产品、设计或技术方向应包含选项、权衡、风险和推荐路径。

终局收敛时，以以下结构收尾：

```markdown
- 推荐：<A/B/C>，因为 <理由>
- 已定决策：<已经确定的内容>
选项：
A) <推荐方向>（推荐）
   好：<收益>
   代价/风险：<代价或风险>
B) <备选>
   好：<收益>
   代价/风险：<代价或风险>
C) <备选，可选>
   好：<收益>
   代价/风险：<代价或风险>
- 开放问题：
```

## 交互规则

- 保持对话推进；不要过度提问。
- 不再提问而直接推进时，把假设说清楚。
- 优先具体例子而非抽象建议。
- 把想法质量与执行计划分开。
- 若用户问"我们下一步该做什么？"，用概念性的下一步选择回答，而不是任务拆解。
