# 基于 DSL 航线编辑脚本的大疆航线编辑 Agent — PRD

> 状态：Draft v0.1 · 2026-08-21
> 来源：flow-requirements 渐进式需求澄清（Decision Map：`docs/dev/decision-map.md`）
> 本 PRD 只写意图（what/why），工程决策（how）留给 flow-design。

## 1. Problem Statement

**谁**：无人机运营平台的航线规划员/演示者——负责把巡检/演示需求画成大疆可飞航线的人。

**什么问题**：
1. **手动画航线繁琐**：传统 B/S 平台（如 yuchen-smart-ops）需在 Cesium 逐点打点、拖拽微调、逐航点配置动作，一条环绕巡检航线耗时数小时。
2. **公司战略转型**：高层判断未来的无人机运行平台是**面向 AI Agent 的原生应用**，传统 B/S 架构逐步淘汰，本产品是 agent 原生试点的第一站。
3. **AI 能力可信兑现**：现有平台"AI 生成航线"多为 mock/规则包装，需要真实 LLM 驱动的生成链路，对外展示"AI 能自动生成航线"。

**不解决的成本**：公司急需展示 AI 能力 + 航线自动生成的进展；手动出线耗时直接拖慢演示准备与巡检交付节奏；agent 原生转型缺乏试点样本。

## 2. Thesis（why build it）

**为什么现在**：GBH 模拟飞行验证平台已成熟，"生成 → 验证"闭环的最后一块拼图已就位；公司战略判断 agent 原生是运营平台转型方向；急需对外展示 AI 能力进展。

**为什么是我们**：yuchen-smart-ops 已具备全部后端真实链路（AirlineContent ↔ open-api ↔ GBH 模拟飞行），缺的只是"真实 LLM 生成"这一层——不是从零造产品，是给已闭环的链路装上对话入口。

**为什么现在能赢**：对内部规划员，把数小时出线降到分钟级且验证标准不变；对演示场景，"现场对话生成一条能飞的航线"是极具说服力的卖点；同时验证 agent 原生应用的技术与流程可行性。

**差异化**：对话式出线 vs 手动绘制——核心是**降低门槛**（自然语言表达需求，不逐点打点）；生成结果走与手动绘制相同的验证链路（GBH），可信度不降级；并作为 agent 原生转型的试点基线。

## 3. Hypothesis

```
We believe: 接入真实 LLM（需求对话 → 结构化意图 → 规则几何 → GBH 验证）后，
航线规划员用自然语言描述需求 → 系统生成环绕巡检航线 → 生成质量达"演示级可用"，
出线时间从小时级降到 10 分钟内。

We'll know we're RIGHT if: 演示现场用对话生成沧海校区环绕线，
10 分钟内出线，GBH 模拟飞行一次通过或 ≤1 次修正后通过，
且展示的是真实 LLM 生成（非 mock）。

We'll know we're WRONG if: 现场生成后 GBH 反复失败（>2 次修正），
或生成结果需人工大幅重画（质量不够、门槛没降），
或生成慢到不比手动快。
```

## 4. Target User & JTBD

**Primary user**：内部航线规划员/演示者（MVP 阶段实质用户是开发者与演示者本人）。

**触发场景**：
- 客户/领导要求演示沧海校区巡检（最高频）
- 日常巡检需求快速出线
- 验证 agent 原生应用的端到端能力

**JTBD**：当 [我有巡检/演示需求，或领导要看] 时，我想 [用自然语言描述需求，而不是逐点打点配置]，这样我就能 [快速得到 GBH 验证通过、可直接下发的航线]。

**Non-users（MVP 明确不服务）**：
- 专业测绘单位（RTK/激光雷达/地形跟随测绘级航线）
- 多机协同/编队场景
- 实时飞行控制

## 5. MVP 范围

### 5.1 产品形态

**独立 agent 原生应用**：对话界面 + 地图预览（生成航线可视化）+ 一键提交 GBH 模拟飞行验证 + 历史航线管理。

### 5.2 生成管线（MVP 形状）

```
用户自然语言 → 多轮澄清缺参 → LLM 提取结构化意图 → 规则几何(环绕 orbit) → AirlineContent
→ 校验 → 地图预览 → 一键提交 GBH 模拟飞行验证
```

- **意图（Intent）**：结构化参数集——区域、形状、高度、速度、动作（拍照/悬停/录像）、云台角、返航配置
- **几何**：MVP 仅**环绕（orbit）**一种形状；直线/之字扫掠后续迭代
- **产物**：AirlineContent，对齐 yuchen-smart-ops open-api-waypoint-route 接口结构
- **验证闭环**：一键提交 GBH 模拟飞行平台，返回验证状态

### 5.3 编辑能力

- MVP 编辑 = **自然语言微调重生成**（如"高度改到100""加拍照""变成两圈" → agent 更新参数重新生成）
- 不做地图手动拖点编辑（传统 B/S 定位，非 agent 原生）

### 5.4 对话交互

- **多轮澄清缺参追问**：缺关键参数（半径/高度/速度/动作）时 agent 反问补齐，每次只问缺失项，参数齐全后生成
- 流式回复，支持解析详情查看

### 5.5 动作范围（最小集）

拍照 / 悬停 / 录像 + 高度/速度/云台角/返航配置，对齐 open-api 动作子集。

### 5.6 落地区域与基准

- 默认区域：**沧海校区**，机巢锚定 22.531635, 113.935066
- 坐标基准：**WGS-84**

### 5.7 持久化

SQLite 落库，历史列表可查看 / 加载续编 / 再次提交 GBH。

### 5.8 失败处理

- 生成/校验失败：agent 定位错误字段，引导用户改正；不伪装成功
- LLM 不可用：规则引擎降级兜底可演示，但**明确标注"非 AI 生成"**

## 6. 非目标（MVP 明确不做）

- ❌ 测绘级高精度航线（RTK/激光雷达/地形跟随）
- ❌ 多机协同/编队
- ❌ 实时飞行控制
- ❌ 空域审批/合规流程接入
- ❌ 地图手动拖点编辑
- ❌ 直线/之字扫掠等几何形状（后续迭代）
- ❌ 全量 11 种 open-api 动作（MVP 仅最小集）
- ❌ 航线版本管理（回滚/对比）
- ❌ LLM 直接生成 KMZ/WPML（绕过结构化产物）

## 7. 成功指标（outcome-shaped）

| 指标 | 目标 | 如何衡量 |
|------|------|----------|
| 出线时间（对话 → GBH 验证通过） | ≤10 分钟（基线小时级） | 现场计时 |
| GBH 模拟飞行通过率 | 一次或 ≤1 次修正 ≥80% | 演示/试用记录 |
| 演示真实性 | 领导确认"真实 LLM 生成"（非 mock） | 现场反馈 |
| 意图提取正确率 | ≥90%（spike 验证） | 测试话术比对 |
| 历史航线续编可用性 | 加载续编无数据丢失 | 功能验证 |

## 8. 技术约束（已拍板，供 flow-design）

| 项 | 决策 |
|----|------|
| LLM | DeepSeek，服务端环境变量持 Key，前端永不接触 |
| Agent 运行时 | **pi agent toolkit（earendil-works/pi）**：`@earendil-works/pi-ai`（多 provider LLM API）+ `@earendil-works/pi-agent-core`（agent loop/tool 分发/事件流/多轮状态） |
| 后端 | **全 TS 单栈（Node/Bun）**：几何生成、GBH 提交、SQLite、HTTP API 全 TS 实现，与前端同语言 |
| 前端 | React + Vite + TypeScript |
| 地图 | 原生 Cesium + 天地图底图（WGS-84） |
| 存储 | SQLite |
| 交互 | 多轮澄清、流式回复 |
| 验证 | GBH 模拟飞行平台（POST /api/open/routes） |

> 注：dm-007 原定 Go 模块化单体已由 dm-012 修订为全 TS 单栈（采用 pi）。详见 `docs/dev/decision-map.md` 与 `docs/dev/research/pi-agent-toolkit.md`。

## 9. 演示验收（Door check）

领导现场：对话 → 10 分钟内出线 → GBH 通过（≤1 次修正）→ 展示真实 LLM 生成。
MVP 技术选型均为 two-way door（可调整），产品形态（独立 agent 应用）为已拍板方向。
