# ADR-0005: 航线编辑器从"对话唯一"转向"对话 / 手动打点 / DSL 脚本三模共存"

- 日期：2026-08-26
- 状态：Proposed（随本 intent PR 由产品负责人接受/拒绝）
- 关联：`docs/intents/three-mode-route-editor.md`；取代 `PRODUCT.md` 中"编辑 = 自然语言重生成…不做地图手动拖点编辑"及硬约束"不做地图手动拖点"。

## 背景

当前产品定位为 agent 原生航线编辑器：自然语言 → LLM 意图 → 几何模板（MVP 仅环绕 orbit）→ AirlineContent → 校验 → Cesium 预览 → GBH 验证。MVP 明确"不做地图手动拖点编辑"，编辑即对话式重生成。

发起人要求把 `yuchen-smart-ops` 中已验证的三块能力迁入本项目：(b) 完整航点工作台（航点 CRUD/拖拽、动作系统、航线参数编辑、KMZ/KML 导入导出）、(c) Python 子集 DSL 的 TS 词法/语法编译器、(d) DSL 与航点绘制的双向联动。这与"对话唯一、不手动打点"的定位正面冲突，必须先裁决定位，否则后续范围与设计无从展开。

## 决策

- 产品从"对话唯一编辑器"升级为**三模混合航线编辑器**：对话、手动打点、DSL 脚本三者均为一等编辑器，读写**同一份航线模型**。
- 任意模式的修改即时反映到另外两者（地图航点 ↔ 动作/参数面板 ↔ DSL 脚本），不存在某模式只写不读或快照分叉。
- **对话保持一等公民地位**：现有 LLM → 意图 → 几何生成管线保留为共享航线上的"几何生成器"之一（环绕 orbit 为首块模板，后续 line/sweep），其产出进入同一可被手动/DSL 继续编辑的模型。演示叙事仍以 agent 对话牵头，三模为同一航线上的不同编辑视角，而非降级对话为一次性生成入口。
- 本决策正式修订 `PRODUCT.md` 的定位与硬约束：删除"不做地图手动拖点"，改为"三模编辑同一航线"。

## 为什么不是其他方案

- **为何不维持"对话唯一、不手动打点"**：当前 demo 仅有环绕模板，无真实航点/动作/参数编辑能力，DSL 与可演示的航线深度不足；成熟的航线规划与 DSL 能力无法在不引入手动编辑的前提下落地，迁移诉求直接被该约束否决。
- **为何不把对话降级为一次性生成入口**：会牺牲本产品作为"公司 agent 原生试点基线"的立身理由，把产品退回为带聊天框的传统航线工作台。三模共存而非取代，保住 agent 叙事。
- **为何不是整体 pivot 为纯脚本驱动**：Python-DSL 是面向"脚本↔航线"故事的编辑视角之一，但纯脚本驱动会抬高使用门槛、削弱地图与对话价值，且源实现本身就是 Python 子集而非完整 Python，不足以承担唯一主编辑器。

## 后果

- `PRODUCT.md` 需更新：定位、运行语境（三栏中"编辑即重生成"段）、硬约束（删"不做地图手动拖点"）、能力清单。该更新在本 intent 接受后、进入 spec 阶段完成，不在本 intent 内改产品文档正文。
- 数据模型从"AirlineContent 为主 + orbit 专用 builder"演进为**统一航线模型**：AirlineContent 仍是权威序列化结构（对齐 open-api-waypoint-route，走 GBH 校验链路），但其上需一层可被三模共同编辑的编辑态模型；orbit builder/validator 重构为该模型的生成器/校验器，不丢弃。
- 风险（冷水，记录在案）：三模并列可能稀释 agent 原生叙事，使产品在领导眼中像"又一个航线工作台加了聊天框"。缓解：对话为默认/牵头入口与演示主路径；三模严格共享模型以体现"agent 编排意图→生成→可被任意视角精修"的闭环；演示脚本以对话开场。
- 这是难逆转的产品边界转向（UI 信息架构、数据模型、叙事均随之改变），故在 intent 阶段即立 ADR，而非拖到设计阶段。
